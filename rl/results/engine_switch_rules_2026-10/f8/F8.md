# F8: does the fork already cover 09e964f's fix 1?

## In plain words

- **Yes, for the case fix 1 fixes.** Upstream's own test, ported, passes on d363ba8's engine (the official engine's source).
- **The case.** Lilligant's Toughness Aroma gives each [G] Pokémon +20 HP. When the Active Lilligant is Knocked Out, a damaged Benched Lilligant loses that +20 and is Knocked Out too. Upstream offered the promotion before noticing the second knockout, so the player could promote into the now-empty slot. Fix 1 removes that stale choice afterwards.
- **The fork never offers it.** It handles knockouts in waves: after each wave's Pokémon leave play, the HP bonuses are refreshed and the board is checked again. So the Benched Lilligant falls in the second wave, before any promotion is built. The promotion is then built from the Pokémon still in play.
- **There is a second, independent guard:** a nested pass after the waves catches any Pokémon left at 0 HP.
- **Which code does it** (planted faults, each in a scratch copy):

  | engine | the ported test |
  |---|---|
  | d363ba8, as committed | **passes** |
  | one wave only (the nested pass still runs) | passes |
  | no nested pass (the waves still run) | passes |
  | one wave and no nested pass (upstream's single pass) | **fails**: 3 promotion choices instead of 2, the emptied slot offered |
  | `prune_stale_bench_activate_choices` not called | passes |

  So either guard alone covers the case. Only with both removed does the fork fail, exactly as upstream did. The prune function rules/09 pointed at is not what covers it.
- **The test catches the bug in upstream too.** Upstream's own test fails at ca4b67f (09e964f's parent: the same 3 instead of 2) and passes at 09e964f.
- **Fix 1 ported as written would do nothing in the fork.** It filters `Activate` choices. The fork offers a forced promotion as its own move, `Promote`.
- **Suggested wording**, for whoever edits rules/09:80 and PLAN.md:26 at step 13 (not edited here):
  > Fix 1: covered in the fork (F8, Oct 1). Upstream's test, ported, passes on d363ba8. Knockouts resolve in waves (`apply_action_helpers.rs:690-820`), with a nested pass after them (`:836-847`), before any promotion is built (`:906`).

## Where, with file:line (all at d363ba8; these files are the same on this branch's head)

`engine/src/actions/apply_action_helpers.rs`:
- **The waves, 690-820.**
  - `handle_knockouts` (665) calls `handle_knockouts_with_prior` (673).
  - Its comment (692-695) names this very case: "Lilligant's Toughness Aroma ... is removed as soon as Lilligant leaves play — which can knock those Pokémon out in turn".
  - The loop (696) asks `get_knocked_out` (943) for each wave (697), stops when one is empty (698-699), and adds each wave to `knockouts` (819).
- **The nested pass, 836-847.** It covers Pokémon left at 0 HP outside the waves' snapshot. It was written for on-knockout retaliation (Innards Out, Final Scream), but it also catches this case (fault "one wave only").
- **The promotions, 897-907.** They come after both, from the full `knockouts` list. `trigger_promotion_or_declare_winner` (906) is called for each Knocked Out Active.
- **The prune, 891-893** (defined 1029-1082). It runs after the waves and touches only ordinary switch frames made of `Activate` and `Noop` choices for one player.
  - It leaves any frame with another move alone (`_ => return true`, 1060), which includes `Promote`.
  - It also leaves a frame alone when that player's Active Spot is empty (1068).
  - So it never touches a promotion.

`engine/src/state/mod.rs`:
- **`discard_from_play`, 1257-1269.** It empties the slot (1267) and refreshes every HP bonus (1268), which is why the next wave sees the second knockout.
- **`trigger_promotion_or_declare_winner`, 1366-1430.**
  - It builds the `Promote` choices from the Benched Pokémon still in play (1396-1403).
  - It inserts them below earlier frames (1427-1428), above a pending second hit (1417-1426).

`engine/src/actions/types.rs`:
- **`Promote`, 161-169.** "Only `State::trigger_promotion_or_declare_winner` constructs this variant."

Upstream, for comparison:
- 09e964f's fix 1 is `src/actions/apply_action_helpers.rs:867-882`, in a `handle_knockouts` that takes one snapshot of the knocked-out Pokémon. Its test is `tests/hp_aura_promotion_test.rs`.

## What this does not settle

- **The fork has no general clean-up of stale `Promote` choices, like fix 1's for `Activate`.** A stale promotion would need a Benched Pokémon Knocked Out by a separate, later step while a promotion waits on the stack. Fix 1's own case can't do that in the fork, as shown above.
- **I did not audit every other path.** I read the attacks that queue Bench damage: Wellspring Dance, Tornado Shot, Double Splash and Triple Bombardment, and `also_choice_bench_damage`. Each queues the Active's hit and the Bench hit in one choice, so a single knockout pass sees both. Mega Kangaskhan ex's second hit waits under the promotion on purpose (`state/mod.rs:1417-1426`).

## The port

- `hp_aura_promotion_test.rs` is upstream's test with one change, for the fork's API: its last check reads `SimpleAction::Promote` where upstream's reads `SimpleAction::Activate`. The board, the attack and every other check are upstream's.
- Upstream's file is beside it, unchanged (`upstream_09e964f_hp_aura_promotion_test.rs`, sha256 `b04806b7…f815`).
- The board: Salandit attacks with Ember (30, +20 for Lilligant's Weakness to [R]: 50). The Active Lilligant is at 80 + 40 HP with 110 damage, so it is Knocked Out. The Benched Lilligant then has 80 + 20 HP with 100 damage, so it falls too. Promotion choices: the two Bulbasaur (slots 1 and 3) only.

## How it was run (`run_f8.sh`, output in `f8_output.txt`)

- `run_f8.sh <work dir> <clone of bcollazo/deckgym-core>` puts `git archive d363ba8 engine` into a scratch folder and adds the ported test. It then runs `cargo test --release --features test-utils --test hp_aura_promotion_test` five times: as committed, then with each fault planted.
- Each fault replaces one exact, unique piece of `apply_action_helpers.rs` in the scratch copy:
  - a `break` after a wave;
  - `if false &&` before the nested pass;
  - the prune call commented out.
- Then it runs upstream's own test at ca4b67f and at 09e964f.
- Every copy is re-stamped before its build. `git archive` gives files the commit's time, older than a previous build in the shared target folder, so cargo could otherwise reuse that build. A first run without this did exactly that, and wrongly showed 09e964f failing. Each section of the output now shows its `compiled deckgym` line.
- The engine copy's `apply_action_helpers.rs` sha256 is at the top of the output.
