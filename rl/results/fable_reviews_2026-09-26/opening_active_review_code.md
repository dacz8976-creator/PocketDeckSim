# Opening Active census and draft (fb12429): review under the code lens

Decision this informs: whether `REGISTRATION_DRAFT.md` in `rl/results/opening_active_census_2026-09-26/` can be registered as written, and whether Fable's provisional call (koa alone by the reserve route, kob/kor as diagnostics, not A+B) survives a reading of the engine source.

Read-only. No build, no engine binary, no game. Everything below was read from the working copy of main at HEAD a3b58a8 (fb12429 is two commits back; `git diff --stat fb12429^ fb12429 -- engine/src` and `git diff --stat 7fc6ccb HEAD -- engine/src/players engine/src/observation.rs engine/src/move_generation engine/src/actions/apply_action_helpers.rs` are both empty, so the engine the draft describes is the official engine's). Card values came from `python lib/card.py`, never from memory. Two throwaway scripts live in the scratchpad (`oa_review/git_show.sh`, `oa_review/recount_openings.py`); nothing in the repo was changed except this file.

## In plain words

- The draft's description of how the bot picks its first Active is right, line for line. I re-derived every number in its Altaria table from the printed cards and the code's constants and got the same ones.
- The proposed change can be kept inside the players' evaluation (tier 2), and k3 stays untouched if the builder gates the new terms the way kq's bench term is gated.
- The "220 of 220" check is true (I recomputed it from the B2c records), but no file in the census folder holds it; it lives only in README prose. That is the one gap the registration should close.
- The rest is wording and builder guidance. Nothing in the draft is false, and nothing I found would let the registration pass while wrong.
- Fable's call stands on the code reading: switch A is one engine flag with one effect the leaf cannot see; switch B is a hand-written table over 52 flag settings with no engine-side definition, and B2c cannot tell it from the readiness reading. A alone as the candidate, B and R as diagnostics, is the reading the code supports.

## 1. Claims checked, with evidence

**k3, kp3, kq3 and kd3 are identical at setup.** Verified.
- k3's value function is `public_clock_effect_value_function` (`engine/src/players/value_functions.rs` 176-187), which reaches `parametric_value_function_ex6` through ex5 with `EvalFeatures::OFF` (421-431). kp3 is the same search inside `PublicPricingPlayer` (`players/mod.rs` 502-512; `public_pricing_player.rs` 113-121). kq3 and kd3 pass `EvalFeatures::KQ` / `::KD` (199-228).
- The setup branch (459-478) returns before any feature is read: kq's bench term is at 527-533, kd's `defender_modifiers` only inside `extract_features` (480-506), which the setup branch never calls. The branch hard-codes `value_aware`'s alternative (463-467, k passes `false`) and calls the online score with `effect_aware = false` (473), so the pricing-mode differences between k3 and kp3 (the text rule at `observation.rs` 478-482; the effect estimator) never enter: a `Place` has no effect text (`observation.rs` 475).
- Both decide through `decision_fn` on a redacted observation (`game.rs` 224-232), and `search_state` (`observation.rs` 144-158) shuffles only the own deck, whose contents are the same either way.

**Root Place moves are searched two own setup moves deep and the setup EndTurn is cut.** Verified.
- Root candidates are scored at `self.max_depth - 1` (`expectiminimax_player.rs` 319-330); each further own action costs one depth (940-960, `depth - 1`); at `depth == 0` with k/kp's `consistent_horizon: false` and `opponent_ply: 0` (`players/mod.rs` 429-430, 508-509) the leaf is `static_eval` (800-906). So the leaf is the placement plus two more own setup actions.
- `EndTurn` while `setup_opponent_hidden` is returned unpriced by `hidden_continuation_reason_in` (`observation.rs` 365-367), applied at 441-454 before any forecast. At the opening only `Place(_, 0)` moves are offered (`move_generation/mod.rs` 143-149); `EndTurn` joins the list only after the Active is down (164). `forced_end_turn` needs `turn_count > 0` (633). The search never reaches turn 1.
- `setup_opponent_hidden` is set by `PlayerObservation::from_state` as `turn_count == 0` (`observation.rs` 50), with the opponent's slots blanked (52). The search state is a clone of that template, so the flag holds at every node the setup search visits.

**The setup score.** Verified: `500 x [every attack of the target form free] + HP / KO points - Retreat`, plus terms equal across openings.
- Weights: `ValueFunctionParams::baseline()` (41-57): `active_pokemon_online_score` 500, `active_safety` 1, `active_retreat_cost` 1, `pokemon_value` 1, `hand_size` 1, `deck_size` 1, `online_pokemon_count` 0, `energy_distance_to_online` 0.
- `calculate_pokemon_value` (1137-1150) sums `HP x (relevant_energy + 1)`; with nothing attached `get_relevant_energy` (1616-1629) is `total - missing` = 0, so the term is the HP of every Pokemon on the own board.
- Online score (1663-1735) with `effect_aware = false`: yardstick = the lexicographically largest attack cost (`.max()` over `Vec<EnergyType>`, 1715-1721) of the highest evolution found in own deck + hand (1676-1693); empty iff every attack of that form is free; then 1.0 (1724-1726), else 0 with no Energy (1729-1734).
- Safety = remaining HP / knockout points (1633-1642); points: Mega 3, ex 2, else 1 (`models/card.rs` 204-216).
- Retreat: `get_active_retreat_cost` with `public_evaluation = true` clones the state, blanks the opponent's board while `setup_opponent_hidden` (640-651), and takes `get_board_retreat_cost_for_player(...).len()` (658), which applies the no-retreat abilities, tools and the two Bench reducers (`hooks/retreat.rs` 110-194).
- Tie: `play_tick` sorts the offered actions by their JSON text (`game.rs` 200-201, `observation.rs` 37-39); `Action { actor, action, is_stack }` (`actions/types.rs` 10-14), `Place(Card, usize)` serialises the card first and `PokemonCard`'s first field is `id: String` (`models/card.rs` 75-76), so two Place moves first differ inside the id string. `max_by` returns the last maximum (`expectiminimax_player.rs` 340-350) and the tie-breaker `prefer_shorter_win(None, None)` is `Equal` (64-71). So the tie goes to the last id in byte order.

**The Altaria numbers.** Recomputed from `python lib/card.py` and the list `decks/research/altaria.txt` (2 Swablu B1 196, 1 Mega Altaria ex B1 102, 2 Eevee B1 184, 2 Espeon B3a 020, 2 Darkrai B2b 040, 1 Igglybuff A4a 059, Trainers otherwise; no Jigglypuff, so Igglybuff's yardstick is its own attack):

| Igglybuff A4a 059 | HP 30, retreat 0, Sleepy Lullaby [-] | itself; every attack free -> online 1.0 | 500 + 30/1 - 0 = **530** |
| Darkrai B2b 040 | HP 100, retreat 2, Dark Slumber [CCC] | itself; costed -> 0 | 100/1 - 2 = **98** |
| Swablu B1 196 | HP 50, retreat 1, Sing [C] | Mega Altaria ex, Mega Harmony [PP] -> 0 | 50/1 - 1 = **49** |

"B1 184" sorts before "B1 196", so Swablu wins the tie. Small Balloon (B3b 064) is a Tool and is not attached at setup. Bad Dreams, Boosted Evolution, Dark Slumber's cost and the evolutions themselves appear nowhere in these terms.

**Boosted Evolution and Bad Dreams are invisible to the score.** Verified. `CanEvolveOnFirstTurnIfActive` is read only in `move_generation/mod.rs` 198-212 (`i == 0`, lifting both the first-turn rule and `played_this_turn`, 209-210) and is passive (`move_generation_abilities.rs` 228). `BadDreamsEndOfTurn` is read only by `hooks/core.rs` 619-631, which walks every in-play holder of its owner, Bench included. The setup branch reads abilities only through the retreat hooks (`retreat.rs` 124-134, 165-194), as the README's second read says.

**The proposed change is confined to tier 2 and k3 is unchanged with the flags off.** Verified as a design; the builder's two obligations are in finding 4.
- The branch the draft targets (459-478) runs only while `setup_opponent_hidden`, i.e. at turn-0 decisions taken through an observation. Nothing in the engine's setup path (`move_generation/mod.rs` 30-42, 140-167; `apply_action_helpers.rs` 47-80; `observation.rs` 48-53, 365-367) needs to change.
- `EvalFeatures` is a private struct with `OFF`, `KQ`, `KD` (234-263); ex5 passes `OFF` for k and kp (430). New fields zeroed in `OFF` (and in `KQ` and `KD`) leave every existing tier on the same code.
- The parse claim holds: no arm before `k<N>` (`players/mod.rs` 165-247) captures a `ko` prefix, and `k<N>` at 248-254 would reject `ko3`; `strip_prefix("ko")` placed before `koa`/`kob`/`kor` would reject `koa3` (the draft says so, section 3).

**"Nothing outside turn 0 changes; only the opening Active can differ."** Verified for A, B and R as specified. The term is read from the own Active only; across the same player's later setup decisions it is constant: A depends on the Active's mechanic and on an evolution somewhere in deck + hand (benching Basics moves nothing out of that union); B depends on `get_in_play_ability_mechanic` (`effect_ability_mechanic_map.rs` 909-917), whose only setup-time suppressor is `SuppressBasicAbilities` (979-985), carried by Alolan Muk B2 097, a Stage 1 that cannot be placed at setup (`python lib/card.py "B2 097"`); `CardEffect::NoAbilities` comes from attacks. R depends on the card. A constant added to every alternative leaves the argmax alone, so the bench and EndTurn choices match kp3's whenever the Active does. Turn 1 and later never enter the branch (`observation.rs` 50).

**"The kp3 probes match the prediction in 220 of 220 informative games."** True, but see finding 1. Recount from `rl/results/altaria_network_divergence_2026-09-26/decisions.jsonl` (scratchpad `oa_review/recount_openings.py`): 235 opening decisions; kp3 opens Darkrai 103, Igglybuff 73, Swablu 56, Eevee 3 (matches `census.json` -> `validation`); under Igglybuff > Darkrai > Swablu > Eevee, no known Basic outranks kp3's pick in any game; 215 games informative counting the network's Active and its setup bench placements, 220 counting kp3's later setup picks too; 0 contradictions either way. The network's order Igglybuff > Eevee > Swablu > Darkrai fits 220 of 235, with 12 Eevee-over-Igglybuff and 3 Swablu-with-Eevee (games 138, 169, 180); 158 openings differ; all as `opening_choice.txt` and README section 5 say.

**The draft's route clauses (a) to (e)** match the fixed text at `docs/REVIEW_2026-09-24_direction.md` line 130 (footprint under 15% set before the census; tau-hat margin 90% lower bound at -1.0 or above and no veto under rule v2; no meta deck's own side worse in the mixed rows; a gain on the new bot's own side and on a non-Dustin top-30 archetype carrying the cards; adoption for screen and table together).

## 2. Findings

Severity: high = a claim in the draft that is false or a registration that could pass while wrong; medium = a gap the registration must close; low = wording. No high finding.

1. **Medium. The "220 of 220 informative games" check has no file behind it.** `census.json` -> `validation` (lines 5463-5496) holds only the per-name count tables that `census.py`'s `validate()` (525-565) computes; `check_census.json` and `census_output.txt` do not hold the informative-game count or the 0-contradiction result either. They appear only in README prose (`README.md` 14, 104-105, 332) and are repeated in section 8's record (REVIEW line 140) as the evidence that the code reading is right. README line 93 points the reader at `census.json -> validation` for this table. The figure is true (recount above). Fix: add the rule check to the census folder as a script and output (the scratchpad `recount_openings.py` reproduces it and can be copied in under the census's owner), or a `validation.<study>.rule_check` block in `census.json` with the informative counts, the contradiction count and the exception games; then point README line 93 and section 5 at it.

2. **Low. README line 241, "Counting only the Basics the network placed, as the first draft did, gives 222 and 1".** With only the network's placements as known Basics the count is 223 fitting and 12 exceptions (11 Eevee over Igglybuff plus game 169); 222 comes out only when kp3's opening pick is also counted as known (game 375's Igglybuff is known only from kp3's pick). Fix: "counting the network's placements and kp3's opening pick, but not kp3's later picks, gives 222 and 1".

3. **Low. "Ties to the larger card id" should say "the later id string in byte order".** The sort is on the JSON text and the first differing byte is inside `id: String` (`models/card.rs` 75-76; `observation.rs` 38), so "P-A 007" > "B3a 020" > "B1 196" > "A4a 059", not a numeric reading. Both scripts implement the string order (`census.py` 386-391 `sorted(hand)`, `check_census.py` 185-190 `sorted(set(basics))`), so no number changes. Fix the wording in README lines 66, 78 and 91 and in the draft's section 4 table note ("tie to the later id").

4. **Low. Two builder obligations the draft should state, so k3's and kp3's identity replay stays bit-for-bit.** (i) Gate each new term with `if features.<weight> != 0.0 { ... }` as kq's bench term is gated (`value_functions.rs` 527-533), not as `weight x indicator` added to the sum: the older tiers then run no `get_in_play_ability_mechanic` or `get_highest_evolutions` call at setup and their float sum is untouched (the identity check compares move hashes, `rl/RUN5.md` 327-328). (ii) `EvalFeatures::KQ` and `::KD` (253-262) must set the new fields to 0/false, not only `OFF`. Fix: add both sentences to draft section 2, "Where".

5. **Low. The unit tests in draft section 4 must go through the observation path.** The setup branch runs only when `setup_opponent_hidden` is true, which `PlayerObservation::from_state` sets (`observation.rs` 50); a test that hands the search a raw `State` (`State::new` leaves the flag false, `state/mod.rs` 539) or calls `decide_omniscient` (`expectiminimax_player.rs` 406-418) would score setup with the battle evaluator and the uncut EndTurn, and the table's rows would not fail for it. `promotion_continuation_tests.rs` 227 shows the pattern (set the flag on the state). Fix: say in section 4 that the constructed hands are decided through `decision_fn` on `PlayerObservation::from_state`, or with `setup_opponent_hidden = true` set explicitly.

6. **Low. Switch A's second condition is inert on every list in scope, and the registration should say so.** "`get_highest_evolutions(&active.card, own deck + hand)` non-empty" is always true for Altaria (2 Espeon in 20 cards, never discarded before setup) and for deck 15, so on the table `koa` is a flat +250 for an Active Eevee. The bot can see its own hand at setup (`observation.rs` 54-56 keep the actor's hand), and B2c's split (README 243-246: +33.7 and +27.9 where the first-turn evolution happened, +17.4 and -2.6 where it did not) is the reason one might want an "evolution in hand" variant. Fix: state that the guard is a list-level safety only and that the hand-aware variant is deliberately not registered now (or register it as one more diagnostic row, decided before any game).

7. **Low. The exhaustive no-wildcard `match` couples tier 1 to tier 2.** Every future `AbilityMechanic` variant (an engine, tier-1 change) will fail to compile until the players' classification is edited in the same commit. The draft presents this as a feature (section 2); the registration should also say who classifies a new variant, that the classification is itself a tier-2 change, and that the phrase test in section 4 is the check. Fix: one sentence in section 2.

8. **Low. Section 7 should name ruling (ii) as a precondition, not only "the reserve route approved".** REVIEW line 160 (commit a3b58a8, after the draft) records that whether a panel archetype may be the (d) carrier is a pending ruling of Dustin's, made once for koa and for kt's Suicune case; the draft's route 1 assumes Mega Altaria ex Espeon. Fix: cite the ruling and say route 2 applies if it goes the other way. The carrier count for (d) (draft 137) is already listed as to-do; it stays a gap to close before registering.

9. **Low. README line 14 quotes only the best-matching cell.** "Darkrai 103.4 predicted against 103 seen" sits beside Igglybuff 73 against 81.6 and Swablu 56 against 45.3 (README 97), which are 1 to 1.7 standard deviations off on the realised deals. The ordering check is exact and is the real test; the plain-words line should quote all four counts or the ordering check instead.

## 3. The call, under this lens

Fable's provisional call is the one the code supports. Switch A is exactly one engine flag with exactly one effect (`move_generation/mod.rs` 198-212), the leaf provably cannot see it, its footprint is Altaria and deck 15, and the two-move horizon cannot reach it (section 6 of the README is right that depth 3 would see it only with the evolution in hand and never a Sleep turn). Switch B is a 52-setting classification written in the players' code with no engine-side definition; B2c cannot separate it from the readiness reading R, and its footprint reaches three decks with no evidence. So: `koa` alone as the candidate, `kob` and `kor` as side-by-side diagnostics, not `ko`. The route question (reserve route with Mega Altaria ex Espeon as the (d) archetype) is not a code question; it waits on Dustin's ruling (ii) and the carrier count, both already named in the draft, plus finding 8's wording.
