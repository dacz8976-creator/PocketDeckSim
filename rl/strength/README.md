# strength: the paired pilot-strength harness

**What it answers.** Is pilot X a better player than the reference, deck by deck and overall, on the *same deals*? It plays every deck under test against every opponent twice: **arm X** (pilot X on the deck, the reference on the opponent) and **arm ref** (the reference on both), from the same seed and seat, so the shuffles, opening hands and first player are identical in both arms. The difference between the arms, deal by deal, is the **paired difference**, reported with intervals, who went first, what each pilot cost in time (and money, for an external pilot), how many more games a given precision would take, and the "intended line" rates. Nothing in `engine/` changes; the harness is a separate crate that links the engine by path.

Dustin (Oct 2): quality first, and the time and cost to get it are reported for him to weigh. So nothing here assumes speed: the number of deals is a parameter, every finished game is checkpointed (a slow run can stop and resume across sittings), a slow pilot is a number in the report and never a failure, and a pilot can be an external process (`ext:`), including one that asks a language model to choose from the engine's legal moves.

## The workflow

1. **Build** (once per engine tree; nice 19, a scratch directory, nothing written into the repo): `rl/strength/build.sh [ENGINE_REF_OR_DIR] [OUT]`. The default is `origin/main`; its `engine/` tree equals the pinned official engine main-8626a35 (tree `38af8b0`), and the script prints the tree hash, the program's sha256 and the harness source hash. **For an experimental pilot, build against its branch's engine** (`build.sh /path/to/experimental/engine`): the harness knows exactly the pilot codes that engine's `parse_player_code` resolves, and the reference `km3` in that build must behave like the pinned one (check: the self-check digest, below).
2. **Pre-register** (before any game): `python3 rl/strength/strength_prereg.py --config CONFIG.json --out RUNDIR`. It validates the decks, writes `manifest.json` (exactly what the program will run) and `PREREGISTRATION.md` (pilots, decks with sha256, seeds, sizes, analysis plan, held-out status, program sha256, repository commit, self-check digests of the engine pilots), and the manifest's sha256. It refuses a directory that already holds games. `config_default.json` is the starting template (the 8 panel lists, the aggro and setup groups, 200 deals x 2 seats; `deals` is just a number).
3. **Run**: `nice -n 19 strength run --manifest RUNDIR/manifest.json --out RUNDIR [--threads N] [--max-games N] [--stop-after-min M] [--only-deck NAME]`. Stop it whenever you like; run it again to resume (a torn last line is repaired). `--dry-run` prints the plan.
4. **Report**: `python3 rl/strength/strength_report.py --dir RUNDIR` writes `REPORT.md` and `report.json`. It **refuses** (exit 1, nothing written) when `manifest.json` is not the registered file (`manifest.sha256` missing, empty, or a different sha256). `--override` writes the report anyway, for a deliberate re-read: it then opens with a `REGISTRATION CHANGED` banner and `report.json` carries `registration_changed: true`.

Keep run directories under `rl/results/strength_<date>_<name>/`, not here. Run from the repository root of a clean tree of the commit you register (a `git archive` or a worktree: the deck files are read and hashed from it).

## Long runs on the laptop: start them with `launch_detached.sh`, list them for `watch_all.sh`

**Every long laptop run starts through `launch_detached.sh`**: strength runs, slow reports, floor and screen runs, and the chain scripts that restart them. Use nothing else. On Oct 8 a forced app update ended the Claude session's process tree, and the run it had started died with it. The launcher gives the run its own session and process group, so it no longer depends on the window, session or app that started it:
- `bash rl/strength/launch_detached.sh start NAME --dir REPO -- nice -n 19 PROGRAM ARGS...` starts it, and refuses if NAME is already running;
- `status [NAME]` and `stop NAME` check it and stop it (SIGTERM to the whole group; the game that is cut off is played again on resume). A run counts as going while its leader runs, or, if the leader died, while a process of its group still carries the run's tag (`LAUNCH_DETACHED_RUN`), so a second start is refused and `stop` still reaches it;
- the pid file and the log are `~/runs/NAME.pid` and `~/runs/NAME.log`.

Rules for the run itself:
- It must be resumable (`strength run` and `slow_report.py` are).
- Keep a chain script in the repository or under `$HOME`, never in a session's scratchpad.

The launcher doesn't keep WSL itself alive. That is the job of the "Pocket Deck Lab WSL On Demand" scheduled task, which holds `wsl.exe --exec sleep infinity` outside the Claude app. If WSL shuts down, start the same command again and the run resumes.

**The status page.** Every 30 minutes the Windows task "PocketDeckSim laptop status" (Dustin approved it, Oct 9) runs `watch_all.sh` in WSL from outside the Claude app. It looks at every run on `~/runs/watch.list` and rewrites `STATUS.txt` on the branch `laptop-status` of origin, readable on GitHub from a phone. **Add a line to the watch list when a long laptop run starts** (`NAME|RUN_DIR|TOTAL|PATTERN|CHAIN|STALL_MIN|X_LABEL`, the header of `watch_all.sh`), and take it out some time after the run is done.
- Each line comes from `run_watch.sh`: games written (complete records only), games since the last look, the last game's time and age, and one state: RUNNING; DONE; WAITING (the chain script runs, the program doesn't: the school-morning pause), or WAITING TOO LONG? past `--wait-max` (900 min); LONG GAMES? (no new game for `--stall-min` while the program is busy) or STALLED? (the same while it is idle); STOPPED; NO RUN FOLDER (a wrong watch-list line). A running program whose chain script has died is marked too.
- The page is rewritten at every look while a run is not done, once more when the last one finishes, and every 6 hours otherwise. Times are UTC. A page much older than that means the laptop could not report: off or asleep, restarted and not signed in yet (the task runs only while Dustin is signed in), offline, or a failing push. `~/runs/watch_all.log` says which.
- The commit is made by git plumbing on a remote-tracking ref only: main's index and working tree are never touched, and no local `laptop-status` branch is made. Read the page on github.com (pick the branch on the web page); don't switch to `laptop-status` in GitHub Desktop, since its only file is `STATUS.txt`.
- **One watcher per run.** `run_watch.sh --push --every MIN`, started with `launch_detached.sh`, is only for a run the task doesn't watch: two watchers of one NAME share its state file and push over each other.
- Tests: `KX_NO_PUSH=1 KX_RUNS_DIR=/tmp/somewhere bash rl/strength/watch_all.sh` looks without pushing; with the default `~/runs` a test would move the real run's "+N in M min" starting point.

## The design in detail

- **Pairing.** A job is (deck, opponent, deal, seat, arm). Deal `i` of the pair at position `p = deck index x 1000 + opponent index` has seed `seed_base + p x pair_stride + i`; each deal is played with the deck in each of `seats`. Both arms of a job share the seed and seat. The report checks that the two arms of every pair started from the same deal (same seed, same first player) and excludes any that did not. A pilot's own search randomness comes from the engine's per-decision seeds (game seed, seat, decision count), never from the gameplay RNG, so a deterministic pilot repeats exactly: **km3 v km3 gives a paired difference of exactly 0** (tested), and the harness's km3 replays 200 games of the official draft A v Fire run game for game, plies included (`rl/results/strength_harness_tests_2026-10-02/CROSSCHECK.md`).
- **Statistic (fixed in the pre-registration).** Game score for the deck: win 1, tie ½, loss 0 (a 30-turn game is a tie). Paired difference `d = score(X) − score(ref)`. Per (deck, opponent), per deck, and pooled: mean of `d` ± 1.96·sd/√n (sample sd, n = paired games), in percentage points. A second pooled figure weights every deck equally. The same by who went first.
- **Runtime and cost.** Per arm and seat: wall seconds per game (mean, median, p95, max), games per second (one thread), decisions per game, milliseconds per decision (mean, median, p95, max), decision time per game; for an external pilot the cost and tokens it reports. Only decisions the engine asks the pilot are timed (a forced single move is resolved by the engine). Times are wall times on a shared machine; with several threads they include contention, which the report states.
- **What more precision would take.** At the sd reached, the paired games needed for ±5 and ±3 points are `(1.96·sd/h)²`; the report converts the games still missing into time at the pilot's mean wall time per paired game and the threads used, pooled and per deck.
- **Intended lines.** `intended_lines.json`: per deck (or `*`), a list of lines with a `kind`: `used_ever`, `used_by_own_turn` (an action by the deck player's n-th turn), `use_with_active` (an action while a named Pokémon is Active), `use_without_point` (an action after which no point was gained before the player's next decision, which is how a knockout shows), `active_at_own_turn` (a named Pokémon Active on a given own turn). Actions are matched by label prefix (`Attack:Turbo Shark`, `Ability:Thieving Incisors`, `Evolve:Mega Sharpedo ex`, `Play:Misty`). Per game: the share of games with the line, per arm, and the paired difference; per use: the pooled rate with a Wilson interval. A new line needs no code: add it to the file (the file's sha256 is in the pre-registration). The log holds the deck seat's real decisions (turn, own-turn number, label, number of legal actions, milliseconds, both points, the Active Pokémon, the Bench size); `log_level full` logs both seats, `none` neither.
- **Held-out group.** `heldout.json` names decks that development never touches. While `locked` is true, `strength_prereg.py` and the program both refuse any deck listed there, on either side, by name and (in the pre-registration) by file content; a held-out run needs `stage: heldout` and the lock lifted by whoever the file names in `unlocked_by`. The list is empty until the design names it.
- **Provenance.** Every run records the program's sha256 (and checks it against the config), the repository commit, the engine description you give it, and a digest of 12 fixed games for each engine pilot (`strength selfcheck`). The same pilot code built against another engine tree must print the same digest: that is the check that the reference `km3` in an experimental build is the pinned `km3`.

## External pilots

A spec `ext:<command>` starts the command (through `sh -c`, one process per seat per game) and asks it for every decision over JSON lines; see `PROTOCOL.md`. It receives the engine's `PlayerObservation` (what the engine's own pilots see: own hand and deck, the public board, the opponent's hidden cards as counts) and the legal actions with compact labels, and answers with an index. It may report a note, a cost and a token count with each answer; the harness keeps them in the game record. `ext_pilot_example.py` is a protocol example, not a player.

## The slow report (opt-in): one deck, kx3, an answer with its uncertainty

`python3 rl/strength/slow_report.py DECKFILE [--deals N] [--no-paired]` answers "how does this deck do with a strong pilot?" (plan: `rl/results/kx3_slow_report_plan_2026-10-06/PLAN.md`). The deck (a file inside the repository, in the deck format: `Energy: <Type>`, then `N Name SET NNN` lines; it is checked with `lib/deck_check.py` first, and a public panel list or a copy of one is refused) is played by **kx3** against the 8 public panel lists played by **km3**, N deals (default 5) x 2 seats each, so 16 x N kx3 games. It pre-registers into `rl/results/slow_reports/<date>_<deck>/` before any game (through `strength_prereg.py`, stage **`use`**), runs with checkpoint and resume, and writes `SLOW_REPORT.md` (the question first, then the size written "N kx3 games + N cheap km3 baseline games", the deck's score overall and against each list with 95% ranges that each say which games they refer to, both pilots and the build, the time it took, and what the numbers can and cannot say) and `REPORT.md` (the engineering numbers). It prints the plan and the expected time first (`--dry-run` prints it and writes nothing); N = 5 is an evening for a typical deck (2½ to 3 hours), N = 10 a night (5 to 6 hours), a Wailord-like wall deck about three times as long (about 9 and about 18 hours: 9 kx3 games an hour against 26 to 34 for a typical deck; the measured cost table is in `PLAN.md`), and on school days the school-morning rule adds a pause from 5:15 am to 5 pm.

- **It never says pass or fail.** No floor cutoffs, no ranking; the screen, the floor and every default stay km3 and are not touched. Every line it prints, the plan, the log and the page name both pilots ("kx3 (d513e37b) on your deck v km3 on the public panel"); a usage error from the argument parser comes before the pin is read and does not.
- **The numbers.** Scores use Wilson 95% ranges (valid at 0% and 100% and for a few games; a unanimous row never shows a zero-width interval); the gain over km3 uses a t interval on the paired differences. The range covers only the luck of the shuffles and coin flips in these deals, not how true to the real game the simulator is. A game that crashed is counted once, left out of every number, and named on the page. A wide range is never waved away: the page says what the games can answer (for the gain, whether the range includes no gain at all) and what they cannot.
- **The km3 baseline is on by default** (`--no-paired` leaves it out). The frozen program plays km3 on the deck on the same deals either way (about a second a game), so the default costs nothing and the page can say how much better kx3 plays the deck than km3. PLAN.md's open point 3 was settled by the coordinator on Oct 7: on by default.
- **The exact tested version.** `slow_report_pin.json` names the frozen build (`/home/dacz8976/kx/strength`, sha256 `5a8f5c83…`, self-check digests of kx3 and km3, the program sha256 those digests were measured on, the engine ref and tree it was built from, and the harness source hash `build.sh` printed for it). A program with another sha256 is refused before a file is written, and the program, the deck, the 8 panel files and manifest.json are checked against the registration again before every sitting. A later version (for example with the Tool tie-break) replaces it only by a new pin, after its own gate. On the pinned binary the self-check text is copied from the pin and the registration says so (`strength_prereg.py` takes `selfcheck_given` only at stage `use`, and only when the text was measured on the program's own sha256); `--selfcheck` replays the 12 games and refuses on any difference (hours for kx3; it is refused during school hours, stopped at the 6:30 cut, and stopped with the wrapper on SIGTERM or SIGHUP). A REBUILD of the same source (the cloud) goes through `--program PATH` (see "Running on the cloud" below).
- **Stage `use`.** For the slow report only (`strength_prereg.py` refuses it without the report's own block, a headline and a pin): a report on a deck, not development, allowed on any deck, recorded as `use` in the pre-registration and the report, never development evidence. A held-out deck may be used, and the held-out guard compares what the engine reads from a deck file, not its bytes or its printed names (each card by set and number, counts merged; the Energy line is left out because with none the engine derives the types from the cards), so a re-exported, respelled or accent-folded copy of a held-out deck or a panel list is still recognised. The lock file is untouched. Because the frozen program refuses any name listed under `heldout_decks`, a `use` manifest lists none there and keeps them under `heldout_registry` and `heldout_in_run`.
- **Realistic knowledge.** kx3 plays the deck knowing its own cards; the deck is never in the pool of lists kx3 guesses its opponent from, and the panel side is never handed it. The environment given to the program has every `KX_*`, `PDL_*`, `DECKGYM_*`, `JEV_*` and `PG_*` variable removed (`KX_EXTRA_LISTS` would add lists to the pool); the list registered with the run is the one used, and the log says which variables were removed.
- **The school-morning rule** (`rl/RUN5.md`): on weekdays no new game after 5:15 am (Chicago time), a program still running at 6:30 am is stopped (the game it was in replays), and the run resumes from 5 pm; weekends are free; the wait is taken in minute steps, and three cuts in a row with no game finished stop the run. `--school-rule off` turns it off (for a machine that is not the laptop), `--school-days mon,tue,...` changes the days. **The choice is made at registration, recorded in the manifest and the page, and carried by the resume command** printed in PREREGISTRATION.md and after a `--max-games` slice (`--school-rule off` is in it), so a cloud resume never idles 5:15 am to 5 pm Chicago time by default; a resume keeps the registered choice unless a flag overrides it. The time zone database is needed when the rule is on (a missing one is a clear refusal at registration or resume, not a traceback hours in) and, for the run folder's date, with a UTC fallback when it is missing; `--school-rule off` with `--date` never touches it. The script never touches git: committing and pushing the folder is the runner's job.
- **Seeds** come from the registered block 24,601,000,000 - 24,699,999,999 (990 slots of 100,000, one per report; see `START_HERE.md`). The picker skips the slots of the other runs in the output folder and the pin's `seed_reserved` ones (684, 685 and 686, the km3 smoke), and registering warns when an unfinished registered run of the same deck is already there (resume it rather than start a second).
- **One wrapper per run folder, and what stops it.** `slow_report.lock` is a kernel lock (flock) that the program inherits, so a second wrapper is refused while either is alive, nothing has to be judged stale, and a wrapper killed with SIGKILL cannot be followed by a second program on the same run (the first one plays on until its sitting ends, or `kill -TERM -<its process group>`). SIGTERM, SIGHUP and Ctrl-C stop the program before the wrapper exits, including during the registration and the self-check, also when the signal arrives while the program is being started (the signals wait until the program can be stopped), and when SIGTERM and SIGHUP arrive together the first ends the call and the other is only noted; a SIGHUP that was ignored at launch (`nohup`) stays ignored, so `nohup python3 rl/strength/slow_report.py ... &` survives the terminal closing. A program that fails or plays nothing stops the run with its message and a partial page. A kx3 report takes hours: run it under `nohup` or `tmux`. The lock file lives in the run folder and is removed when the wrapper ends; do not commit a folder whose wrapper is still running.
- **Resume and report.** `slow_report.py --dir RUNDIR` continues a stopped run (it refuses a manifest that is not the registered file, a missing or empty `manifest.sha256`, a checkout that has moved since registration, and any option that belongs to a new registration); `--dir RUNDIR --dry-run` says where it stands and whether it would be refused; `--report-only` rewrites the page from the games so far, marked PARTIAL while games are missing; `--max-games N` plays N games in total across both arms (about N/2 of them kx3 games; across school-morning cuts) and stops. Tests: `cd rl/strength && python3 -B -m unittest -v test_slow_report test_slow_report_runloop test_slow_report_process test_slow_report_page test_slow_report_registration test_strength_prereg_use test_strength_report test_slow_report_existing`.
- **A page from games that already exist.** `python3 rl/strength/slow_report_existing.py --deck NAME --dev DEVRUN --tool GATE3RUN --out DIR` writes `SLOW_REPORT_EXISTING.md`: the same questions asked of existing development evidence (the pinned build's development run and gate 3 of the Tool tie-break), labelled "existing development evidence, not a fresh test", never the km3 floor check, with no pass or fail line. It plays nothing and changes no source; it refuses a run that is not the pinned build, a gate-3 build that does not replay the development run's km3 baseline exactly, or a manifest that no longer matches its recorded hash. The Wailord demonstration is `rl/results/slow_report_demo_wailord_2026-10-07/`.

### Running on the cloud (a rebuilt program, no school rule, slices)

The pinned binary lives on the laptop; the cloud builds its own copy of the same source. The route is supported and checked. **The pin must be the committed one**: `slow_report.py` refuses any pin that is not byte-equal to the `rl/strength/slow_report_pin.json` committed at HEAD of the repository it runs from (a hand-edited pin, or `--pin copy.json`, could make any program look pinned; the only way round is the test-only variable `SLOW_REPORT_ALLOW_UNCOMMITTED_PIN`, which is recorded as "bypassed" on the console, the page and PREREGISTRATION.md). Console, page and PREREGISTRATION.md say "pin committed: yes" with the pin's sha256. If git refuses the folder as unsafe (a clone made by another user, as in a root container: "detected dubious ownership"), the refusal quotes the first line of git's own message and the `git config --global --add safe.directory <folder>` line that fixes it, instead of just saying the pin is not committed. The check reads the repository it is told about even when `GIT_DIR` and its relatives are exported (a git hook, `rebase --exec`). The same holds for a hand-written `use` config run through `strength_prereg.py` directly: a self-check text it gives must be the committed pin's own text for that pilot (a copied one must also be one the pin says was measured on this program), or it is refused before anything is written. A text said to be replayed needs a program route that fits the program (the pinned binary, or a rebuild whose build record is on disk beside it and is the one the block carries), and the committed pin is asked for whenever the block carries a pin state or a route, with a text or without.

1. **Build the pinned source.** The commit `d513e37b473f2819075e1eb2439075a8a1e65c42` is on the branch `origin/claude/playout-pilot`, so the cloud's clone needs that branch (`git fetch origin claude/playout-pilot`), and `build.sh` builds with `cargo --offline`, so the dependencies must already be in the cargo cache (fetch them first, with network, against the lock file of the pinned commit and not of whatever checkout you are in: `mkdir -p /tmp/d513 && git archive d513e37b engine | tar -x -C /tmp/d513 && (cd /tmp/d513/engine && env CARGO_HOME=$HOME/.cargo cargo fetch --locked)`; the fetch names the cache the build reads, `CARGO_HOME=$HOME/.cargo` as in the build command below, because an image may set its own `CARGO_HOME` (the rust Docker images use `/usr/local/cargo`) and a fetch without it would fill a cache the offline build never looks in). Build to **a path of your own, never the pinned binary's** (`/home/dacz8976/kx/strength` on the laptop: a rebuild does not reproduce its sha256, so overwriting it ends the pinned route for good; `build.sh` and `slow_report.py` both refuse that path). Pin the things the result depends on, so the same command can be repeated after a restart: `env HOME=$HOME CARGO_HOME=$HOME/.cargo STRENGTH_BUILD_DIR=$HOME/slow_report_kx3/build STRENGTH_TARGET_DIR=$HOME/slow_report_kx3/target bash rl/strength/build.sh d513e37b473f2819075e1eb2439075a8a1e65c42 $HOME/slow_report_kx3/strength`. It prints the engine tree **as archived** (git's tree id of the files that were extracted and compiled), the program sha256 and the harness source hash, and writes **`strength.build.json`** beside the program: engine ref and tree, harness hash, program sha256, `rustc -vV`, `cargo -V`, the machine and libc, HOME, CARGO_HOME and the build folders, and the exact `rebuild_command`. The output path is a file, not a folder (a folder is refused); the build folders and the output path may be given relative, the record and the rebuild command carry them absolute. `build.sh` takes the variables that change what cargo builds out of cargo's environment (`RUSTFLAGS`, `CARGO_PROFILE_*`, `RUSTC_WRAPPER`, `RUSTUP_TOOLCHAIN`, ...; the record lists the ones that were set, so the printed rebuild command does not depend on them), lists the cargo config files that still apply with their sha256, allows one build at a time per build folder and per target folder (locks held by the script alone), and stops with exit 1, no program and no record when cargo fails (it never hands out the program of an earlier build). It does not pin the C toolchain (`CC`, `CFLAGS`), the system libraries or the toolchain behind rustup's default, so the same bytes need the same machine setup, which is why step 5 is not a guarantee. The tree id is of the bytes that are compiled: attributes (a `.gitattributes` in the engine, the machine's attributes file) are switched off in the scratch repository that computes it, and the harness hash is of the copies that were compiled, not of the checkout as it is when the build ends. Build on a Linux file system: the executable bit is part of the tree id and `build.sh` reads it from the file system (`core.fileMode=true`), and a build folder on a Windows drive under WSL (DrvFs without metadata) reports every file as executable, so the tree would not be the ref's and the rebuild would be refused rather than wrong; the record says which kind of file system the build ran on (`build_fs`, from `stat -f`). The record is written by this script and is **not signed**: it binds itself to one file by sha256 and says what the builder did; what stands behind the program are the replayed self-checks in step 2. **The engine tree must be `31dbd2e6e8ec…` and the harness source hash `bf9c5d68…`** (the pin's `engine_tree` and `harness_source_sha256`); `--program` checks both from that record, not from the checkout. The program sha256 will normally differ from the laptop's `5a8f5c83…` (a rebuild is a different binary even on the same machine), which is why the replay in step 2 is the check.
2. **Register only**, with the rebuilt copy and the choices for a cloud run. The registration replays the kx3 self-check, which takes hours, so give it the nohup form and look at the log: `nohup python3 rl/strength/slow_report.py DECKFILE --program $HOME/slow_report_kx3/strength --deals 10 --threads 4 --school-rule off --register-only > register.log 2>&1 &` then `tail -f register.log` (`--dry-run` first prints the plan, and the pin and build-record lines, without replaying anything). When the program's sha256 is not the pinned one, `--program` needs its build record (refused without one, or when its program sha256, engine tree, harness hash or engine ref is not the file's / the pin's), forces the replay of **both** self-checks (kx3 and km3) on that machine, which must equal the committed pin's digests (kx3 `31d638dbc818b0fa`, km3 `81b572198c04d5d1`; a non-zero exit is a refusal too), and refuses unless this checkout's harness source is the pinned build's; nothing is written on a difference. The page and PREREGISTRATION.md then say the program is not the pinned binary, that its build record says it is a rebuild of the pinned source (unsigned), and name its sha256, the build record (toolchain, paths, rebuild command), "self-checks replayed on the registering machine" and the harness source hashes. Registration ends by printing the command that plays the run (it carries `--school-rule off`).
3. **Commit and push the registered folder** (`rl/results/slow_reports/<date>_<deck>/`) before any game: that is the pre-registration, and it is what a restarted container checks out.
4. **Play in slices**: run that command with `--max-games N`; the wrapper stops after N games across both arms (about N/2 of them kx3 games), writes the page (marked PARTIAL), releases the lock and prints "stopped after --max-games N (games across both arms, about half of them kx3 games); resume with: <command>". **Commit and push the folder between slices** (do not commit while a wrapper is running: the lock file is in the folder).
5. **After a container restart**: check out the pushed folder **at the same absolute path** (the manifest records the checkout's path), fetch again what step 1 needed (`git fetch origin claude/playout-pilot` for the pinned commit and the same `env CARGO_HOME=$HOME/.cargo cargo fetch --locked` on the pinned commit's lock file as in step 1, both with network: a restart brings back a clean checkout and cargo cache), and make the program exist again with the registered `rebuild_command` (it is in the build record shown on the page, in the manifest's `slow_report.build_record` and in `strength.build.json`: same toolchain, HOME, CARGO_HOME and build folders as the first build), then run the resume command. A resume goes on with the same program sha256. If the rebuilt copy has another one (a different toolchain, path or image changes the bytes; on one machine two real rebuilds of this source in different build folders differed, while the recorded command run again from scratch gave the first build's bytes back, see the smoke folder), a run registered on the rebuilt route may still go on, and only if the pin in use is the pin the run was registered under (same engine tree, harness hash, engine ref and self-check texts) and is the committed one, the new program's build record has the same engine tree as archived and the same harness hash as the pin, and both self-checks are replayed again (hours for kx3) and equal the committed pin; it is then logged as a `program_changed` event (old and new sha256: the program the previous sitting ran with) and the page says "The program changed mid-run" with how many games ran before and after. `--dir RUN --dry-run` makes the same checks before it says a resume would replay and go on (or "it would be refused: ..."). A run with every game played is not replayed for a changed program (the page is written from the games). A run registered on the pinned route needs the same program byte for byte. Whenever a registered run is read again (`--dir`), what its registration says about the program is checked against itself (a pinned-route registration must carry the pinned binary's sha256 as its program's, a rebuilt-route one a build record for that very program with the engine tree as archived and the harness source the registration names) and, while the pin file in use is the one the registration was made under, against that pin (a later pin is not asked): a resume or a dry run refuses a registration that fails, and a `--report-only` page flags it in "What was run". The program and its build record are read again after the replay, and the change is refused if either is not what was replayed. The page also says when a sitting went back to an earlier accepted build (the registered one or an earlier change: no replay is needed, no change is logged). The `program_changed` lines of `slow_report_log.jsonl` are checked against the registration (rebuilt route, written for this run: the sha256 of its `manifest.json` is in the line, build record with the registered engine tree and harness hash, the registered self-check texts), so a stray, foreign or pasted line is neither honoured nor shown on the page (a line written before lines named their run counts when the `registered` line of the log names this run's manifest); that is a consistency check, not authentication (whoever can write the run folder can rewrite `manifest.json` and `manifest.sha256` as well): the pushed commit of the registration is the tamper evidence. Anything else is refused, naming both sha256 values (the games already pushed stay valid for `--report-only`; a new run needs a new registration). The deck, the 8 panel lists and manifest.json are checked again too.
6. **Finish**: the last slice writes `SLOW_REPORT.md` and `REPORT.md`; commit and push them.

## Limits

- A game that reaches the engine's 30-turn cap is a tie and counts ½.
- The intended-line log has the pilot's real decisions only; an action the engine forces (a single legal move) is not logged. `EndTurn` is always legal, so attacks and abilities are always logged.
- The pairing is exact only for deterministic pilots; a sampling external pilot adds its own variation to `d`, which is what the interval measures.
- The harness plays whatever rules the engine tree it was built against has. The reference and the pilot must come from the same build; an experimental branch must leave the engine rules as they are, or the comparison is not against the official engine.
- Games are independent, but a deck pair's deals share an opponent list and seeds across arms by design; the interval treats paired games as independent draws.
