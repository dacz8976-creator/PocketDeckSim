Codex's video frames (jpg/png) in `Battle Logs\Recording_QA` are choking OneDrive. This tool deletes the frames of game packets whose results are safely in the repo, and, separately, moves **only `Recording_QA`** (the frames and the packets) out of OneDrive. **The videos are not moved: they stay where they are, in OneDrive, so they keep their cloud copy.** It deletes nothing else.

## The retention rule

| what | rule |
|---|---|
| **Text outputs** (json, txt, md: ledgers, reviews, deck files, receipts, scripts) | permanent. The tool never deletes one. |
| **Frames** (jpg, jpeg, png inside a game packet) | may be deleted once their game is **in the repo**, its positions **passed review and a person accepted that** (below), the packet's own text outputs are still in its folder, and **the source video is still in Battle Logs**. Frames can be cut again from the video as long as the video stays. |
| **Videos** | stay while their game has an open shot-list or rules question and through its season. The tool never touches a video, and neither step moves one: none is inside `Recording_QA` (the 203 videos, 112 GB, are in `Reviewed\` and at the top of `Battle Logs\`), and `--move-to` takes only `Recording_QA`, so the videos stay in OneDrive with their cloud copy. Deleting videos is a separate decision this tool does not make. |

## "In the repo" is not what the first brief said: read this first

The brief said a batch's "ledger/packet files" are committed on main under `rl/results/pause_games_*`. **They are not.** `TURN_LEDGER.json`, `REVIEW.md`, `DECK_USED.json` and the rest of a packet exist only in `Recording_QA` (and OneDrive). What is committed is what was *derived* from them: per result folder a `games_meta.json` (game, title, the packet's folder `BATCH_x/<packet>`), `positions_all.json` (the converter's positions), the decks and the km3 tables. So the rule below uses "the game's positions are in the repo", and because the ledgers are not in the repo, the tool also requires the packet's text outputs to still be in the folder before its frames go (they are permanent; this only checks nobody removed them). The text outputs themselves are being copied into the repo by `tools/battle_logs_import_packets.py` (`rl/results/battle_log_packets/`), which the move step requires to be current.

There are **19** `BATCH_*` folders in `Recording_QA` (not 124), and **65,775** image files in all (about 46,300 in game packets of batches, 19,427 in 105 other folders such as `RETROSPECTIVE_HANDS_2026-10-02`, the old `*_sol` folders and `Luckycad_*`). Only the batches are in scope; the rest is listed in the dry run and never touched.

## The rule, per game packet

A **game packet** is a directory directly inside a `BATCH_*` folder whose name starts like `20261013_030351000_iOS`. Everything else in a batch (`__pycache__`, `qr_support`, `STALLED_INTAKE_LOCK_*`, `LIVE_UPDATE_*`, and image files at the batch level such as `LIVE_SAVE_SUMMARY.png`) is **never touched**, even in a batch that is deleted; the dry run counts them.

The frames of a game packet may go only when **all five** hold; the dry run prints the failing ones as the reason:

1. **In the repo, with positions.** `BATCH_x/<packet>` is the `folder` of a game in a `games_meta.json` committed under `rl/results/pause_games_*/` (any depth), and the `positions_all.json` in the same folder holds at least one position for that game. (Four games of BATCH_2026-10-06 are in a `games_meta.json` with **no** positions, because Codex found no exact 20-card list: 214518, 214731, 034229 and 012140. They stay, and the audit list keeps them in `pending`.)
2. **Audited.** The game is in the `games` of the committed audit list `rl/results/battle_logs_retention_2026-10-14/audited_games.json` under the same folder, **and the entry names the same `games_meta.json`, the same number of positions and the same sha256 of those positions (their content) that the repo has now**. If a later commit changes any of them (for example a regeneration of `positions_all.json` that keeps the count), the game is held back as "not audited as it is now". "Passed review" is a judgment about records, not something a program can read out of a markdown review, so it is a list a person owns (next section).
3. **Accepted** (checked by `--apply`; the dry run prints the status). The audit list's `confirmed` field is a structured acceptance of exactly the `games` listed now (below). It is Dustin's decision, so `by` must be his name (`Dustin` or `Dustin via the laptop`); a free-text string, `"no"`, `"pending"`, `"false"`, `"not yet"`, a number, a boolean, another name or an object with any key besides `by`, `date` and `games_sha256` (for example `"withdrawn": true`) is not an acceptance.
4. **Text outputs present.** `TURN_LEDGER.json`, `REVIEW.md` and `DECK_USED.json` exist in the packet and are not empty.
5. **Source video present.** The packet's `SOURCE.json` names its video (`video_basename`) and its size (`bytes`, a positive whole number: without it a truncated copy cannot be told from the video) and some copy of that file in `Battle Logs` (top level or `Reviewed\`) has exactly that size. A packet that does not say which video it came from, or how big, is held back too. The video is looked at **again just before the packet's first frame is deleted** (a video removed or cut short while the question was open leaves that packet's frames and the run exits 1). The tool looks in the folder given by `--videos PATH`, else in the one recorded in the moved `Recording_QA` by `--move-to` (`BATTLE_LOGS_LOCATION.json`), the folder `Recording_QA` is in, and `C:/Users/dacz8/OneDrive/Desktop/Battle Logs`; the report's second line says where it looked.

**A packet that records more than one game is held back WHOLE** unless every game in it passes on its own. Packet `20261006_012927000_iOS` records two games: Codex's `RELATED_GAME_PACKETS.json` says `root_is_only_shared_writer_and_media_mover: true`, and game 2's own evidence files cite 124 frames in the packet root's shared `native/` folder (43.5 MB, 71 of them inside game 2's interval), besides the 142 in `game_02/`. So the tool does not try to tell which root frame belongs to which game: if the packet says it holds more than one game, none of its frames go (1,272 frames, 536 MB for this one). "Says" means the largest of `RELATED_GAME_PACKETS.json`'s `game_count`, its `game_packets[]` / `games[]` entries (both layouts Codex wrote), `other_games_found: true`, `SUMMARY.json`'s `source_game_count`, and 1 + the second-game folders found (a path in that file other than `.`; a `game_NN` folder; a sub-folder with its own `TURN_LEDGER.json` and a `SUMMARY.json` whose `game_id` differs from the packet's). A declared second game whose folder cannot be found holds the packet too. The second review of the layouts is deliberately wide: `RELATED_GAME_PACKETS.json` as a list at the top, `game_packets` / `games` / `packets` / `related_games` as a list of paths, of `{path | packet | folder}` objects or as an object keyed by path, a count written as a string, `SUMMARY.json`'s `game_count` / `games_in_source` / `match_count` / `games` (a number or a list) as well as `source_game_count`, folders named `game2` / `game_2` / `..._game_03`, and one folder spelled two ways on the case-insensitive Windows drive (counted once, in the spelling on the disk). A RELATED file that is not valid JSON, or that exists but says nothing about how many games the packet holds (no `game_count` of 1, no `other_games_found: false`, no root entry), holds the packet back, and so does an unreadable `SUMMARY.json`. **Each second game's own `TURN_LEDGER.json`, `REVIEW.md` and `DECK_USED.json` must be present and non-empty too** (checked again just before deletion, with the packet's own). Not covered: a second game in a sub-folder with a name no rule knows, whose `SUMMARY.json` is absent (such folders are not told from a backup copy by anything but their name); on the real data none exists (all 72 packets were read). The packet goes only when each second game is in the repo and audited under **its own** folder (`BATCH_x/<packet>/game_02`), with the same acceptance; then its frames go with the packet's. The dry run says `stays <packet>: holds 2 games; game_02 (142 frames) is not audited: ...`. Folders that keep an earlier state of a game (`original_before_*`, `submitted_before_*`, `before_*`, `independent_sol`, `rejected_*`) are not second games and go with the packet; a `game_NN` folder inside one of them is never deleted (the report lists it as staying).

"Committed" means read **from git at one commit**: the ref (default `origin/main`, meaning the remote-tracking ref `refs/remotes/origin/main`, never a local branch of that name) is resolved to a commit once, and every file of the rule is read from that commit, not from the working tree, so a file that exists only on someone's disk or branch does not count. The report prints the commit and its date. `--apply` accepts only `origin/main` and asks origin (`git ls-remote origin refs/heads/main`, never a password prompt) whether that is what origin has now: if the remote is ahead (for example the audit list was revoked, or only committed here and not pushed) it refuses and says to `git fetch origin`; **if origin cannot be asked it refuses too**, unless `--allow-offline` says to go on with the `origin/main` this checkout has. The question is asked again after the typed answer, so a revocation pushed while the prompt was open still counts. Git is run with `--no-replace-objects` (a local `git replace` cannot change what "committed on origin/main" says), and a checkout whose `origin` is fetched from one URL and pushed to another is refused (what it fetched may be a stale mirror).

A batch is **DELETE** when every game packet in it passes, **PARTIAL** when some do, **keep** when none do or it has none. The unit of safety is the game packet; the batch line is a roll-up. This differs from the brief ("batches marked delete") on purpose: nearly every pause batch has a straggler (a game with no positions, a second game), and all-or-nothing would keep 6 GB of good frames in BATCH_2026-10-06 for the sake of 0.7 GB. `--whole-batches-only` restores the literal reading (only DELETE batches).

### What `--apply` removes, and what it cannot

- Only files ending `.jpg`, `.jpeg` or `.png` (any case), at any depth **inside a game packet that passes**, outside any second game recorded in that packet. Never json, txt, md, py or any other file; never a video; never an image at the batch level or in a non-game sub-folder; never anything outside `Recording_QA`; no folder is removed.
- The plan re-validates every path. **Immediately before each frame is removed, its whole folder chain below `Recording_QA` is looked at again, uncached** (every component a real folder, none a symlink or junction, and `Recording_QA` still the folder that was checked before the question), so a folder renamed, moved out or replaced by a junction while the run is going is noticed at the next file (the frame is counted as failed and left alone). On a native Linux file system the file is then removed through a **directory handle** (opened with `O_NOFOLLOW`, one folder at a time, only the handles of the folder being emptied stay open), compared with the folder at its path first; on the mounted Windows drive (9p, where a handle is resolved by name and followed a swapped-in junction in the second review) and on native Windows Python it is removed by its path right after the check. Just before a packet's first deletion its required text outputs (and its adopted second games') must still be there and non-empty, and its source video must still be the recorded size, else the packet is skipped (and logged).
- Links are never followed. Only *name-surrogate* reparse points count as links on Windows (symlinks and junctions); every OneDrive file carries a plain reparse attribute and is an ordinary file for this purpose.
- **Before the question** the tool lists every non-frame file of the packets with its size **and SHA-256**; after the deletion it lists them again. If one is missing or its content changed, it says `INTEGRITY CHECK FAILED` and exits non-zero.
- The log goes to `Recording_QA\CLEANUP_LOG_<UTC time>.jsonl`, written **line by line** (line-buffered, with an fsync at the start, at the end, and every 1,000 files): the header names the committed state and commit, who accepted, and each packet with its game key, `games_meta` and position count; then one line per file removed (written right after the removal), failures, skipped packets, and a last line with the totals and the integrity result. It is a text file, so it is permanent too.
- **If the run is interrupted** (Ctrl-C, `SIGTERM`, `SIGHUP` when the terminal closes) the signal only sets a flag, checked between files, so the file being removed is always counted and logged first. The log gets an `interrupted` line whose count agrees with what is gone, the tool prints `interrupted: N deleted, integrity check not run`, and exits 130; run `--apply` again to finish (what was already deleted is simply not there). The same holds for a signal during the final integrity pass (the line says `during: checking`; the deletions are all logged, the check was not finished). A signal that was set to be ignored stays ignored, so a `nohup` run survives its terminal closing. `SIGKILL` cannot be caught; the line-buffered log still has every line written.
- **Exit code:** 0 only when every planned frame was deleted, no packet was skipped and the integrity check passed. If some deletions failed (a file held open) or a packet was skipped, it prints `INCOMPLETE ...` and exits 1.
- Progress is printed every 1,000 files.
- OneDrive sees the deletions like any others and removes the files from the cloud (they stay in its recycle bin for a while).

## `--move-to PATH`: only Recording_QA

`--move-to C:/Users/dacz8/BattleLogs/Recording_QA` moves **only** the `Recording_QA` folder (the frames and the packets) out of `Battle Logs` to PATH, which becomes the new `Recording_QA` folder, and prints the path Codex should use. **The videos and everything else in `Battle Logs` (the 203 videos, 112 GB, `Reviewed\`, `Original_OBS_Recording\`, `MEDIA_LOCATIONS.json`, the review notes) stay where they are, in OneDrive.** The dry-run report and the move's own output both say so, and list what stays. It is a **rename on the same drive**: instant, nothing is copied, nothing can be half-moved. It refuses when:

- the folder to move is not named `Recording_QA` (the tool never moves `Battle Logs` itself or anything else);
- PATH is relative, or directly in a drive root (`C:/Recording_QA`), or already exists (even empty), or is inside `Recording_QA` (compared without regard to case, the way NTFS does), or neither its parent nor the folder above the parent exists (one missing parent folder is created, and the output says so; it is removed again if the rename fails);
- PATH has lost its backslashes on the way through `wsl` (a drive letter not followed by `/` or `\`), or does not end in `Recording_QA` (the moved folder keeps its name; a lost separator merges the last folder into the one before it, as in `C:/Users/dacz8/BattleLogs\Recording_QA` arriving as `BattleLogsRecording_QA`);
- PATH is on another drive (that would be a copy of everything; the tool does not do it);
- the source is a symlink or junction to a `Recording_QA` rather than the folder itself (renaming it would move the link and leave the data in OneDrive), or two `Recording_QA` folders exist at the default places and `--qa-root` does not say which;
- PATH is inside a OneDrive folder (`--allow-target-in-onedrive` says it is meant), or its parent would have to be created and has the name of an existing sibling folder with more letters stuck on (`C:/Users/dacz8BattleLogs` next to `C:/Users/dacz8`: the signature of a lost backslash);
- the rename fails (something has files open: Codex, Explorer, OneDrive sync). Nothing is changed in that case.

It asks you to type `MOVE` and **repeats the target path in that prompt** (`--yes` skips this; with `--dry-run` it only prints the plan, which commit its import check read, and that origin was not asked). Before it moves it lists what will go stale and edits none of it: the scripts and text at the top of `Recording_QA` and of each batch that name the old `Battle Logs` path or `MEDIA_LOCATIONS.json` (a file that stays behind), and the repo's files that name `OneDrive\Desktop\Battle Logs`. It also says that scripts which reach files by a path *relative* to `Recording_QA` (`..\Reviewed`, `..\MEDIA_LOCATIONS.json`) cannot be found by a check and will break. After the move it prints the new `Recording_QA` path for Codex and writes `BATTLE_LOGS_LOCATION.json` into the moved folder (where the videos stayed: `--videos` if given, else the folder an earlier move recorded, else the one `Recording_QA` was in), so the tool finds the source videos in later rounds (a record that is not valid, not absolute, or names a folder that is not there is a printed warning and is ignored); run it afterwards with `--qa-root <that path>` (and `--videos <Battle Logs>` if that file is missing).

**What leaves OneDrive: the import must be current before the move.** Moving `Recording_QA` out of OneDrive removes it from the cloud, including the packets' **text outputs** (ledgers, reviews, deck files, receipts). Those are the permanent part of the retention rule and existed nowhere else. They are copied into the repo by `tools/battle_logs_import_packets.py` (`rl/results/battle_log_packets/`, with a manifest; its README has the details), so GitHub is their backup. **Run that import again, commit it and get it into main immediately before the move, because Codex keeps writing new files** (the last check found 56 new and 3 changed text files). `--move-to` enforces this: it hashes every text output of `Recording_QA` and refuses unless each one is committed on `origin/main`, byte for byte, under `rl/results/battle_log_packets/` (git's own blob ids are compared), and says how many are not; with `--dry-run` it only shows that. The check follows `--apply`'s rule: `--no-git` and any other `--ref` are refused for a real move (an import that sits only in the working tree, or in a local commit that was never pushed, is not a backup), origin is asked whether its `main` is what this checkout has (refused if it differs or cannot be asked, unless `--allow-offline`), and it is asked again after the typed `MOVE`. The check is strict: a text output the import would skip (over 50 MB, a path too long for a Windows checkout), a folder or entry the scan could not examine (not readable, a link, a reparse point) and a `Recording_QA` with no text outputs at all are problems, not passes; it is **run again after the typed `MOVE`** (Codex keeps writing, and the answer may take minutes), reusing the hashes of files that did not change; and it prints a WARNING listing the files that are neither text outputs nor images (zips, audio, vendored folders) which are not copied into git and leave OneDrive's cloud with the folder. `--no-import-check` skips the check, at your own risk. **Pause OneDrive and close Codex's sessions before moving.**

## Not done, not known

- **Native Windows Python is untested.** The tests and the dry run ran under WSL (Linux Python on `/mnt/c`, also the whole test file on a Windows-drive mount, including a real junction made with `cmd.exe`). The Windows-only parts (reparse tags, the path-based removal without handles, `os.rename` on NTFS inside OneDrive) are written but have not run under Windows Python. That is why the README runs it through `wsl`.
- A second game in a sub-folder whose name is no backup name and no `game_NN` and that has no `SUMMARY.json` of its own is not found. The files that say how many games a packet holds are read in every layout seen or likely, and an unreadable or silent one holds the packet, but a folder like that is not told from a backup by anything but its name. None exists in the 72 real packets.
- A frame that two games share inside one recording cannot be told apart by the tool, so a two-game packet goes whole or not at all (above). If packet 012927's 1,414 frames (0.56 GB) matter, game 2 has to be read and audited under `BATCH_2026-10-06_NEW_PAUSE_GAMES/20261006_012927000_iOS/game_02`.
- The audit list is Sonnet's proposal; no one has accepted it. The tool will not delete until someone does.
- Frames in the 105 folders outside `BATCH_*` and the videos are outside this tool. The text outputs are backed up by the separate import tool, which the move requires to be current.
- A game with positions in the repo can still have been converted from a ledger that is later corrected; its frames are then gone and only the video can answer. That is the cost of the rule and why videos stay through the season.
